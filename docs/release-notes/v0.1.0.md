The first public release of **Open CAM Studio** — a CAM application for CNC
toolpath generation, written in Rust.

It takes a DXF or DWG drawing, gives you a live 3-D view of the toolpaths and the
material being removed, and writes G-code for your control. The 2.5-D milling
slice works end to end. Everything beyond it — 3-axis surfacing, turning, a plugin
ABI — is roadmap, not present.

## What it does

**Eight operations** — profile, pocket, face, drill, thread milling, chamfer,
engraving and V-carving. Leads and ramp/helix plunges, engagement-capped area
clearing, and per-operation cutting parameters.

**V-carving uses two tools in one operation.** The boundary outlines an *area*
rather than a path: the tool never touches it, its flanks land on it, and the
depth follows from the shape's own width. An end mill clears the flat land the
depth cap leaves behind, then hands over to the V-bit, which finishes the wall and
cleans the corners a round cutter cannot enter.

**Tool suitability guards.** Every operation checks that the surface doing the
cutting *is* a cutting surface, by reading each tool's own profile rather than
matching on its type. Engraving with a chamfer mill — whose tip is a flat that
does not cut — is refused, as is cutting past the flute length onto the shank.
Choices that are merely poor warn and proceed.

**Six post-processor dialects** in three output families: grbl / FluidNC /
grblHAL, LinuxCNC, and Fanuc / Haas. Helical arcs where the control supports them.

**Geometry in** — DXF and DWG import with contour chaining and hole nesting,
including open paths for lettering, plus AutoCAD-style object snaps when picking.

**A tool library** of 36 starter tools, grounded in real catalogue geometry
(DIN 338, DIN 6527, and the Amana router-bit catalogue) rather than invented, so
the guards, the cross-section preview and the depth limits behave as they would on
real steel. Every cutter kind is fully characterised, with flute, shank and neck
geometry.

**Material simulation** — a profile-aware heightfield showing what the tool
actually removes, including for pointed tools, whose width at a given depth is the
width of the cone there.

| macOS Apple silicon | `OpenCAMStudio-v0.1.0-macos-arm64.dmg` |

Each has a `.sha256` beside it. The Linux build requires **glibc 2.35 or newer**
(Ubuntu 22.04, Debian 12, or later).

**The binaries are not code-signed**, so macOS and Windows will both warn on first
launch. That is expected. The README explains how to proceed, and the checksums
let you verify you have exactly what CI built.

## What has actually been tested

Being straight about this, because "it builds" and "it works" are different
claims:

- **Linux and Windows** — installed and run by hand: the AppImage, the MSI
  (install, Start Menu entry, clean uninstall) and the portable executable.
- **macOS** — builds and packages cleanly, and CI verifies the bundle structure,
  the property list, the architecture and that the disk image mounts with the
  application inside. It has had less hands-on use than the other two.
- **The pipeline itself** — 599 automated tests, plus byte-level golden files for
  posted G-code and property tests that bind inputs no golden covers.

Verification here means auditing exported `.nc` against the post's dialect, line
by line. That practice found four defects in V-carving alone that the test suite
had not, one of them a machine-safety issue — so if you find G-code that looks
wrong, please open an issue with the file. That is the loop that works.

## Known limitations

- No 3-axis surfacing, no turning, no plugin ABI yet.
- macOS is Apple silicon only; there is no Intel build.
- Nothing is code-signed.
- Collision checking for pointed tools is resolution-coupled: fidelity depends on
  the cell size being chosen for the narrowest cut.
- A carve beside a circular island can overcut by about 18 µm, because the
  flat-land boundary is a polygon approximating a circular offset. Inherent to
  polygonal offsets; logged rather than chased.
